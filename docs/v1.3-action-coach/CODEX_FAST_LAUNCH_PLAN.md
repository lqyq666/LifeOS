# LifeOS V1.3：历史执行计划

> 2026-10-05 用户重新定义后，本计划的旧范围、固定模型与顺序不再生效。当前唯一产品验收见 ../../PRODUCT.md，当前实现依据见 ../../.planning/research/campus-growth/BRIEF.md。保留本文用于解释旧组件、失败证据与已完成安全验证。

## 1. 已决定的路线

继续现有 LifeOS：React/TypeScript 界面、现有认证、Node 对话核心、PostgreSQL、已接入的离线语义检索和单份行动材料。**本轮不接入、分叉或搬运 AstrBot，不另建一套聊天服务、记忆平台、Agent 编排或模型网关。**

这不是要求所有通用设施自研：TLS、数据库、认证、模型 SDK、嵌入等继续使用已有合适组件。只有当前缺口明确、许可与数据边界清楚、能减少剩余工作时才引入一个必要依赖，不为“成熟框架”再开迁移项目。

完成顺序：先让真实复盘到可执行成品成立，再验证真实部署环境，最后通过明确授权的公网首发与外部验收。邀请制控制访问规模，不降低核心功能与安全要求。自动支付与公网可用是不同状态，不拿其中一个冒充另一个。

## 2. 不可牺牲的产品价值

帮助用户还原具体经过，辨明事实与未知，协作准备一项能立即开始、投入可承受的行动。用户拿到产物后，不应还需要重新设计“找谁、怎么开口、具体做什么”。不是承诺执行不花力气，也不是保证别人配合或项目成功。

用户说“我做了上次的行动，但对方没有使用”时：

- 优先找回对应事件；确有歧义才核对，不重复询问已有身份和经过。
- 区分原计划与实际执行，并核对“不使用”的判断依据。必要时沿对象选择、如何联系、原需求、具体说法与回应、约定、实际制作、交付与使用环节深入。
- 这些是理解维度，不是固定顺序、固定轮数或必须填完的问卷；一到两个紧密相关的问题可以同轮问，不能用问号数量判质量。
- 用户记不清或拒答时只保留相应未知；愿意继续则核对另一关键环节，不因此擅自转向心理解释或下一次重做。用户明确只要眼下成品、暂停或倾听时尊重短路径。
- “打不开”只能支持接触受阻，不能证明内容无效；“没回复”不能当作拒绝。疑问句也不能偷偷预设未经支持的原因。
- 事实足以支持眼前动作时结束追问，实际起草可发送的话、邮件、代码、材料片段或步骤。不用“去沟通/去验证/优化资料”替代成品。必要信息缺失就问清或明确给模板，不把空占位称成品。
- 改短、改语气或改变约束时，实际修改同一行动版本；显示、保存与复制内容一致。回来反馈时接回这件事，而不是另开新故事。

过程清楚、依据边界清楚、行动准备已完成，才是闭环。记录了结果、增加了版本号、生成了卡片不等于闭环完成。

## 4. 第一里程碑：把真实核心闭环做通

### 4.2 收敛对话，不增加框架

重点检查 `turn-prompt.ts`、`turn-engine.ts`、`action-coach-events.ts`：

1. 从实际Provider上下文核对当前输入、角色、原事件、已问/已答和未知。先定位是缺信息、错误状态、指令冲突还是模型选错问题。
2. 对话策略用简洁统一的原则和少量与验收故事不同的示例，替换累积的重复禁止条款；不在每次失败后再加一个专用关键词补丁。
3. 用现有事件节点区分明确观察、用户转述、感受、用户解释、未知、已回答和拒答。先前建议不是已执行事实，相似事件不是当前事件。没有新变化不重复写同一过程。
4. 一轮围绕一个关键环节，可以问两个紧密关联的问题。不强制问完所有维度；也不因看见一个交付障碍就跳过仍会改变下一步的原需求/沟通。
5. 明确执行请求直接交付；更新的是同一个行动对象，不只改版本。保留来源和材料一致性，不强制新假设/新卡片。
6. 初次合格请求应只有一次生成；不在主路径加分类、规划、自评、总结四个模型。必要时用现有更强模式，但不以额外推理掩盖错误上下文。

模型选择不以“最便宜”锁死，也不随意更换平台。先修明确根因；如候选之间仍需比较，只使用已有授权模型，对相同用户上下文、同一任务与协议做一次有上限的对照，保留所有结果和差异。单样本不宣布可靠。已有非思考DeepSeek结构失败、自然文本只复述的诊断不作为生产采用证明。不新增无条件模型级联或第三次调用。

### 4.3 拆分可独立的失败，不牺牲安全

在 `validateOutput`/`stageCandidate` 处理独立可选经历候选：回复/事件/行动/引用已经合法，唯一问题只是未来计划或技能误提为经历且与主要结果无依赖时，拒绝候选、记录原因，原事务仅提交其余合法结果，不为此多调用一次。

权限、跨账户、撤回、更正版本冲突、主要材料错误或引用错误仍阻断其依赖结果。用户明确要求保存经历、正文声称经历已保存等情况不能悄悄降级。所有被拒绝的字段不落库，也不显示保存成功。保留真正经历提取与用户确认的正测，不靠关闭功能取得通过。

### 4.4 真实演示必须覆盖

A01：模糊反馈 → 原需求/联系/实际经过 → 核对不使用依据 → 有边界的判断 → 可发送材料。
A05：一次给足过程 → 直接材料 → 实际改短/调整 → 同一action和正确版本。
A06：只倾听/拒答/暂停 → 不强制复盘或行动。

这三条先收口，再扩展A02–A04不同原因、A07历史召回与更正、A08校园具体执行，以及已要求的来源生命周期验证。既有合成事实不得泄漏给模型；需要时按对应问题提供。改写或新例在运行前固定，不能让模拟用户临时编造有利证据。

首个里程碑交付的是可打开的候选预览和真实对话/材料证据，不是又一份大规划。阶段候选必须标明未完成整版验收。

## 5. 第二里程碑：速度、验证效率和最小首发访问控制

### 5.1 让有效内容提前出现

保留目前一次生成、必要增量协议；不要凭一次自然文本诊断改成不保存事件的纯聊天。也不让反复抄ID/旧内容占据大部分输出；服务器能可靠确定的信息由服务器负责，来源选择和版本保护仍保留。

在现有流中记录请求接收/排队结束/检索完成/Provider开始/原始首块/安全有效片段就绪/实际展示/生成完成/校验/提交。完整中性问题可作为未提交草稿先显示，敏感前提、外部引用、已发送/已保存声明须等相关验证。失败、取消或更正时撤回草稿。不要把原始JSON、加载状态或无意义复述算首内容。

不要无边界展示所有未验证文字，也不要继续用越来越长的“允许句首”列表代替正确的流式解析。普通因果前言不得误挡后面独立中性问题；问题本身仍要防止夹带未经支持的断言。

保留普通真实追问至少20个样本：首有效内容p50≤3秒、p95≤5秒，完成p95≤15秒。长材料事先单列；同一最终配置的轨迹内普通轮可以同时贡献速度样本，不重复花钱跑相同内容。未达到数字如实不通过，不能排除失败样本刷成绩；同时报告追问是否真正推进。

### 5.2 删除重复能力探测的耦合

当前 `model.ts` 的能力签名包含业务prompt和renderer。最小改为：
- 接口能力签名：模型、端点、SDK、结构schema、传输、关键参数、流式/取消能力。
- 行为/发布签名：prompt、上下文构造、renderer、检索及校验代码、固定事实/用例、运行配置。

纯业务提示改动且接口等价有本地证明，可复用原真实接口能力记录，不改写原报告；每次新行为仍需对应回归。接口/模型实际变化时，只验证受影响能力，最终做一次完整链路。失配/失败凭证不得放行，不能直接把守卫设成true。

### 5.3 上线必需的访问控制，保持小

首发采用真实账户加邀请码/人工开通，默认不开放无限注册。增加一个最小服务端权益记录和受保护的运维入口即可，不做商城/CRM/复杂后台。

账号有效期、使用上限、剩余量、合理限流和全局费用熔断可配置。每请求先预留权益，合法回复事务提交时扣一次；内部repair不扣第二次。取消/失败释放预留，已提交但客户端断线重取原结果，不重复扣、不重复请求模型。数据库计数是权威，不信任前端。浏览、复制已保存材料、修正、遗忘与确认不计模型对话额度。

并发、重复requestId、取消和余额边界用模拟Provider测，不用付费压测。该权益是运营控制，不改变深入复盘目标，不能为了省额度故意少问。

## 6. 第三里程碑：补齐真实部署，不只交付本地ZIP

### 6.1 修正已发现的打包缺口

检查当前Dockerfile/compose/启动链，不原样沿用旧镜像。干净构建至少包括：

- 前端构建实际引用的全部文件（包含跨目录的服务端类型依赖），运行端所需的脚本和文件；不能依赖宿主机node_modules。
- 可复现的Linux CPU Python依赖、BGE固定revision及完整摘要；模型在构建/准备阶段下载核验，运行时离线加载，不上传用户文字，不在首个请求临时安装/联网拉模型。
- 正确的缓存/模型只读挂载和必要可写运行目录，非root权限。当前512MB限额不能未经测量就宣称足够；实测冷启动、常驻RSS和目标并发，设置合理资源，不擅自购买升级。
- 新版模型能力证据与当前配置对应；不复制旧backend能力报告来假装V1.3已验证。构建镜像不包含API Key、真实私聊、私有数据库或本地账本凭据。
- 应用、数据库、嵌入worker健康与就绪区分；嵌入未就绪时明确降级或暂不接受相关请求，不能伪装长期记忆完整可用。
- 删失效环境变量/脚本引用前核对消费者；不移除实际安全配置。

用新的compose项目名、隔离库和独立端口测试，不复用或停止55432/8790。保留PostgreSQL持久卷、版本化迁移及恢复验证；迁移单次受控执行，失败不自动破坏性回退。干净容器能启动、登录、检索、回复、保存、重启后继续，才称可部署。机制回归可Mock，真实外部烟测另行计费并标识。

### 6.2 公网首发前条件

首阶段即核对本项目可用的部署目标、域名、DNS权限、TLS方式、部署地区及对应上线条件。不为绕过地域要求更换地区，不由Codex虚构“合规已通过”。相关公开规则按实际地区/供应商官方要求核验，真实需要用户确认的资格/条款单列。

所有代码与配置就绪后，给用户一个合并的最小发布确认：目标资源、公开地址、将变更内容、现有数据影响、费用、回退方案。得到明确授权后只对该目标部署。缺少授权/资源时完成可独立的工作，状态为READY_TO_DEPLOY_WITH_BLOCKERS，不假装上线。

正式环境要有HTTPS、正确Origin/Secure Cookie/反向代理信任，API Key仅服务端，SSE代理不缓冲且超时合理，数据库不暴露公网，管理员访问受保护。日志默认只留必要计时/状态/用量，不记录完整私人正文。提供与实际实现一致的隐私说明、服务边界、删除/遗忘及联系途径；不承诺不存在的备份物理抹除。

部署后从另一客户端/外部网络核验真实域名：邀请登录→复盘→材料复制→改写→退出后继续→更正/遗忘；检查断线恢复、重启持久化和错误可见性。再验证一次回退/恢复路径。localhost、截图、HTTP200和health绿灯均不能单独代表ONLINE_VERIFIED。

### 6.3 付费状态不要混淆

最快先让邀请用户完整使用核心产品，同时限制额度。**INVITE_LIVE不等于PAID_LIVE。**

若已有明确获准使用的商户/支付渠道，在核心通过后只接一个渠道，复用官方SDK或托管收银台，完成服务端订单、回调验签、重放/金额/订单状态校验、权益发放幂等、退款/撤销和对账。先测试环境，真实扣款另行授权。套餐价格/轮数/有效期必须由用户确认后对外承诺。

缺少商户或支付授权时，不做假支付、不自行接个人收款绕过渠道要求，也不阻止非付费邀请上线；交接明确“支付未完成”。未来¥0.99与约¥10仅为定价候选，不能把它当已售权益。公网用户运营预算另行确认，不能拿剩余研发调用额度当无限生产预算。

## 8. 完成判定与交付

核心验收必须同时满足：
1. A01–A08必需行为、来源生命周期和关键安全回归通过；A01深入关键过程，A05不盘问已知事实，A06尊重暂停。
2. 同一个真实事件与行动跨轮/跨会话承接，改写实际生效，来源撤回无复活，确认后才能进入图谱。
3. 最终配置的普通真实速度达标，明确报告所有失败与样本；不得以跑得快的无效复述通过。
4. 干净容器可复现启动，离线检索依赖齐全，最终构建/类型/安全/迁移恢复/1440和390/320正式浏览器通过。
5. 权益、限流、幂等、取消、重启与备份符合首发使用要求。

代码自动检查通过后，仍需用户亲自看一条真实复盘和改写，不让Codex代替用户点击“接受”。修复阶段与权限检查不必每步请示；只有费用、外部资源、上线授权、支付与人工接受这些真正的边界一次说明。

状态按证据分别报告：CORE_READY、DEPLOYMENT_READY、FOUNDER_ACCEPTANCE、INVITE_LIVE、PAID_LIVE；任何一项未过就写原因，不把邀请上线叫付费上线，不把本地准备叫公网上线。若核心仍失败，整体继续NOT_READY，即使镜像已经完成。

交付只需：一个最终源码提交、一份可恢复源码与必要证据包、一份HANDOFF。手册包含启动与部署、Python/模型资产校验、当前域名和镜像摘要（存在时）、权限与运行预算、备份恢复/回退、真实对话、速度费用和未完成项。不要嵌套多代ZIP，不打包私有环境和数据库。
